# Configuration

[Back to README](../../README.md) · [Reference index](README.md)

The root `orchid-sdd.yml` is generated by `setup`/`migrate init` and validated by
the CLI. The published contract is
`.skill/schemas/config.schema.json`. Unknown keys are errors. Paths are relative
to the project root and must not leave it.

After editing:

```bash
orchid-sdd doctor
orchid-sdd doctor --fix   # if the config hash is stale or dirs are missing
```

## Acted on by

| Value | Meaning |
|---|---|
| **CLI** | The command reads, validates or enforces it now |
| **Agent** | The orchestrator/`SKILL.md` consumes it; the CLI stores and validates it |
| **Policy** | A documented guardrail/convention; the current CLI does not mechanically enforce it |

Changing a path after data exists means moving the directory and keeping manifest
artifact references valid. Prefer setting paths at setup/migration time
(`--knowledge-folder`, etc.).

Changing `project.profile` later does not regenerate personas, tests or the
profile constitution pack; edit those surfaces directly or rerun setup
deliberately.

## Steering

Steering is the phase-aware layer for architecture, examples, language-agnostic
style, principles and repository rules. The constitution remains the baseline for
how code is written; steering names the explicit project decisions that
Discovery and Logic Review must check. Rules are Markdown files with front matter,
resolved by ID like personas. The front-matter contract is published at
`.skill/schemas/steering.schema.json`.

| Key | Default | Meaning / values | Acted on by |
|---|---|---|---|
| `steering.enabled` | nine core rule IDs | Rules available to the project; disabled IDs cannot be phase-mapped | CLI/Agent |
| `steering.search_paths` | `.orchid/steering`, `domains/*/steering` | Project rule directories; one-level `*` | CLI |
| `steering.overrides.<ID>.authority` | rule default | `advisory` or `blocking` | CLI/Agent |
| `steering.overrides.<ID>.phases` | rule default | Phase list override | CLI/Agent |
| `steering.overrides.<ID>.file` | — | Load a rule file for this ID (relative to project root) | CLI |
| `steering.phases.<phase>` | seeded map | Ordered active rule IDs for `discovery`, `assessment`, `planning`, `build`, `code_review`, `logic_review` | CLI/Agent |

The seeded phases are:

```yaml
steering:
  phases:
    discovery: [architecture-boundaries, solid-principles, dependency-inversion-container, code-style, code-examples, repository-flow, saga-pattern, discovery-steering]
    assessment: [architecture-boundaries, solid-principles, dependency-inversion-container, code-style, code-examples, repository-flow, saga-pattern]
    planning: [architecture-boundaries, solid-principles, dependency-inversion-container, code-examples, repository-flow, saga-pattern]
    build: [architecture-boundaries, solid-principles, dependency-inversion-container, code-style, code-examples, repository-flow, saga-pattern]
    code_review: [architecture-boundaries, solid-principles, dependency-inversion-container, code-style, code-examples, repository-flow, saga-pattern]
    logic_review: [architecture-boundaries, solid-principles, dependency-inversion-container, code-style, code-examples, repository-flow, saga-pattern, logic-review-steering]
```

`steering context --phase P` returns the ordered rules, their source files, example
paths and the artifact path where the agent records evidence. A rule may declare
default `phases`, but the phase mapping is authoritative. Run `doctor` after
editing; it rejects unknown, disabled or duplicate references.

See [Steering](steering.md) and [Patterns](patterns.md).

## Models and efforts

Model routing is declarative and separate from steering. It records which effort
level a phase or development prompt expects, and which agent/model should provide
that effort. It does not launch, switch or control a model.

The effort enum is the task-size dimension:

```text
low | medium | high | extra-high | ultra
```

| Effort | Typical task shape | Example routing intent |
|---|---|---|
| `low` | Rename, docs, mechanical edit | Fast/cheap model; minimal review |
| `medium` | Normal feature with known boundaries | Default implementation model |
| `high` | Cross-cutting change, non-trivial design | Stronger implementation/review model |
| `extra-high` | Architecture, migration, security-sensitive work | Strongest model; independent review |
| `ultra` | Incident, high-risk or ambiguous work | Human-led; strongest model plus escalation |

The table describes intent, not a hard-coded model list. You choose the
agent/model for each effort.

| Key | Default | Meaning |
|---|---|---|
| `models.default_effort` | `medium` | Fallback when a phase has no assignment |
| `models.mismatch` | `warn` | `warn` always alerts; `block` fails on a confirmed mismatch |
| `models.efforts.<effort>.agent` | unassigned | Expected coding agent or harness; optional |
| `models.efforts.<effort>.model` | unassigned | Expected model identifier; optional |
| `models.phases.<phase>` | phase defaults | Effort for `intent`, `discovery`, `assessment`, `planning`, `build`, `code_review`, `logic_review` |
| `models.prompts.P-###` | — | Prompt effort, or a phase-to-effort map |

```yaml
models:
  default_effort: medium
  mismatch: warn
  efforts:
    medium:
      agent: opencode
      model: openai/gpt-4.1
    high:
      agent: claude-code
      model: anthropic/claude-sonnet-4
    extra-high:
      agent: claude-code
      model: anthropic/claude-opus-4
  phases:
    intent: medium
    discovery: medium
    assessment: high
    planning: high
    build: high
    code_review: high
    logic_review: extra-high
  prompts:
    P-001: high
    P-002:
      build: high
      code_review: extra-high
```

Effort definitions are optional: an effort with no `efforts` entry falls back to
`models.default_effort`. If neither the requested effort nor the default has a
usable mapping, the route is `unassigned`. A development prompt may also declare
`effort` in its front matter. Resolution is:

```text
models.prompts[P-###] (config)
  → prompt front matter effort
  → models.phases[current phase]
  → models.default_effort
```

A prompt's `estimate: S|M|L` is a planning estimate, not a routing key. Routing
uses `effort`; set it explicitly when a prompt needs a different tier from its
phase default. A practical starting point:

| Plan estimate | Suggested effort |
|---|---|
| `S` | `low` or `medium` |
| `M` | `medium` or `high` |
| `L` | `high` or `extra-high` |

The CLI does not infer effort from estimate; the plan author decides.

Set the current identity explicitly when the harness does not expose it:

```bash
export ORCHID_CURRENT_AGENT=opencode
export ORCHID_CURRENT_MODEL=openai/gpt-4.1
orchid-sdd route --phase assessment
```

Or pass `--current-agent` and `--current-model`. If the expected model/agent is
configured but the current model cannot be recognised, the command prints an
alert and the agent must tell the user.

With `models.mismatch: block`, `prompt start` refuses a confirmed mismatch. With
`warn`, the mismatch is reported and the human decides. Routing is a declaration,
not a launcher: orchid-sdd never switches a model or an agent.

### Routing across handoffs

`handoff prepare` preserves the active prompt, run, step and routing. After moving
to another harness, `resume` rebuilds state and accepts the latest handoff; it
then shows whether the new identity matches the expected effort. This lets a small
prompt stay on a fast/cheap model while a high-risk or cross-cutting prompt moves
to a stronger one without losing the work context.

## Execution

| Key | Default | Meaning / values | Acted on by |
|---|---|---|---|
| `execution.max_parallel` | `4` | Maximum simultaneous prompts in a wave; enforced by `prompt start` | CLI/Agent |
| `execution.isolation` | `worktree` | `worktree`, `clone` or `branch`; wave execution requires `worktree` | Agent/CLI (doctor) |
| `execution.require_clean_tree` | `true` | `start` refuses a dirty root/repo | CLI |
| `execution.integration_branch` | `orchid/{iteration}/integration` | Feature/integration branch used only when the user opts in; otherwise prompts merge into the current branch | Agent |
| `execution.release_strategy` | `squash` | `squash`, `pr` or `none` at closure | Agent/Policy |
| `execution.merge` | `orchestrator` | Who performs merges | Agent/Policy |
| `execution.max_fix_loops` | `3` | CR fix attempts before escalation | Agent |
| `execution.test_commands.unit` | profile default | Unit test command | Agent/Setup |
| `execution.test_commands.integration` | profile default | Integration test command | Agent/Setup |
| `execution.test_commands.e2e` | profile default | End-to-end test command | Agent/Setup |

At Intent, the skill asks whether to create a feature branch and which base branch
to use (`main`/`develop`; default `project.default_branch`, or `develop` for
Git-flow). If the answer is no, it stays on each affected repository's current
branch.

Every implementation/test prompt uses one disposable worktree and temporary
branch (`orchid/<iteration>/<prompt-id>`), deleted immediately after CR and merge;
spikes use `spike/<prompt-id>` and are discarded. Closure verifies that no prompt
branch or worktree remains.

### Parallel waves

A wave is an independently executable slice of the prompt DAG.
`orchid-sdd wave start <N>`:

1. checks that every dependency is `done` or `waived`, and that a dependency is
   not still in an unreconciled active wave;
2. proves the wave's write scopes are disjoint, including against other active
   waves;
3. freezes one base commit per affected repository;
4. creates one worktree and branch per prompt;
5. marks the prompts `ready`.

It does not launch agents. Start up to `execution.max_parallel` prompts with
`prompt start`; each prompt keeps its own worktree and context. Several
independent waves may be active on the same root.

`start` owns the full clean-tree guard; `wave start` ignores the intentionally
dirty state, events, matrix and runtime paths, but refuses uncommitted code unless
`--allow-dirty`, because worktrees freeze `HEAD`. Run `orchid-sdd` commands with
`--root <project root>`, not from inside a prompt worktree.

`orchid-sdd wave reconcile <N>` merges the committed prompt branches in wave
order, optionally runs the effective `execution.test_commands.unit` with `--test`,
deletes the worktrees and branches, and emits `wave.reconciled`. Spike prompts run
on `spike/P-###`; reconciliation copies their findings under
`assessment/spikes/` and discards the branch instead of merging it.

A conflict or failed test marks the wave failed and leaves the evidence in place.
Fix the branch (or the test), then rerun the same `wave reconcile`; already merged
prompts are recorded by `wave.merged` events and are not merged twice.
`wave abort` removes the remaining wave artifacts and fails its prompts; it does
not rewrite commits that a previous partial reconcile already merged. G5 and
closure refuse to proceed while a wave is active or a prompt branch/worktree
remains.

Every state mutation, including event appends, takes an exclusive lease at
`.orchid/locks/state.lock`. The lease records owner, PID, host, purpose and
expiry; a live owner blocks with a clear error, a crashed owner or expired lease
is reclaimed, and nested calls in one CLI process share the lease reentrantly. The
event log remains single-writer, so manifest, matrix and index projections cannot
be raced by parallel agents.

## Resolution order

```text
Config:      root orchid-sdd.yml is authoritative; workspace.repos[] declares repo
             metadata and repo fragments are validated repo policy for the agent
Personas:    inline overrides → project files → search_paths → skill defaults
Steering:    inline overrides → project files → search_paths → skill defaults
Constitution: project → profile pack → skill default (agent-level)
Templates:   .orchid/custom → .skill defaults (agent-level; `diff` audits)
```

The CLI does not merge repo fragments into the root config. It validates them and
leaves the fragment as the repo-specific policy the agent reads for work in that
repo.
